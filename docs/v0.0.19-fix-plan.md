# v0.0.19 Fix Plan

Date: 2026-10-16
Source: `docs/v0.0.19-review-findings.md` (do not edit that file — it is the

checklist).

## How to use this document

- This is a living checklist, executed one commit at a time, in order
  (later commits assume earlier ones in the same group have landed).
- Every unchecked box is a `[ ]`; check it to `[x]` only once the change is
  committed, not when it's merely written.
- **Changelog rule:** every commit that changes behavior in `aether.h`,
  `iris.h`, or `hermes.h`, or changes any public doc (`README.md`,
  `docs/*.md`, `TODO.md`), gets a `CHANGELOG.md` entry under `## [Unreleased]`
  in the *same* commit as the fix, written in this project's existing
  verbose-prose style (see current `### Fixed`/`### Changed` entries for
  tone — explain the bug/gap, the fix, and why, not just "fixed X"). The only
  commits exempt from this are pure test-harness or release-tooling changes
  that no downstream consumer would notice (flagged explicitly below where
  that applies) — if you disagree on a given commit, say so when it comes up
  rather than silently skipping the entry.
- **Commit boundaries are explicit.** Each numbered item below ends with a
  `STOP` line. At each `STOP`, the agent presents the diff and the drafted
  commit message and waits for review and an explicit go-ahead before
  running `git commit` — never commit past a `STOP` unprompted, and never
  batch multiple numbered items into one commit unless told to.
- **Decision points are explicit.** Any item marked `DECISION NEEDED` is not
  mechanical — the agent must stop and ask before writing code, present the
  options listed (or better ones it finds), and only proceed once a
  direction is chosen. Don't guess past one of these.
- Items without a `DECISION NEEDED` marker are expected to be mechanical
  given the finding's description in `docs/v0.0.19-review-findings.md` — but
  if source reading turns up something the finding didn't anticipate, stop
  and ask rather than improvising past it.

### 2. Fix the release gate's blind spot to asserts

`AETHER_BUILD_DEBUG` defaults from `!defined(NDEBUG)`
(`aether.h:180-186`), and CMake's `Release` config defines `NDEBUG` by
default — so `scripts/release.ps1`'s only build+`ctest` gate
(`release.ps1:80-82`) always runs with every `AETHER_ASSERT_` compiled to
`((void)0)`. It cannot catch any assert-based bug, including the three
Group-2 bugs below, no matter how long they've shipped.

**DECISION NEEDED** — options to put in front of the user, pick before
writing anything:
  - (a) add a second Debug configure/build/`ctest` pass before the existing
    Release build+package step (simplest, closest to current structure,
    doubles the script's run time — acceptable for a manual release script)
  - (b) force `-DAETHER_BUILD_DEBUG=1` into the existing Release build's
    compile definitions, so one build gets both optimization and live
    asserts — cheaper, but means the artifact that gets tested is no longer
    byte-identical to the artifact that ships (asserts baked into the
    installed static lib/DLL, if those targets are part of what's packaged)
  - (c) something else the user prefers

  **Decided: (a).** A separate `build-debug` configure/build/`ctest` pass
  runs before the existing Release build+package step.

- [x] Implement the chosen approach in `scripts/release.ps1`
- [x] No CHANGELOG entry (release tooling, not library behavior)
- [x] **STOP — review & commit.** Committed. (Verified against a scratch
      Debug build before committing: the new gate correctly fails on the
      same 3 known bugs — confirms a Release-only gate would have shipped
      them silently.)
