# Pre-0.1.0 Review Findings — aether.h / iris.h

Date: 2026-09-01
Scope: `include/aether/aether.h` (2861 lines), `include/iris/iris.h` (818 lines)
Methodology: four parallel review passes (correctness/safety, performance, API
consistency/naming, ergonomics/docs/structure), each reading both headers in
full, followed by manual spot-verification of the highest-stakes claims
against source and `docs/iris-networking-design.md`. Nothing in this file has
been acted on yet — it's a findings list, not a plan.

## B. Correctness — landmines (correct today, fragile under the next edit)

- `aether.h:1491` `arena_push` — the overflow check's third clause
  (`size > reserved_size - aligned_pos`) only avoids unsigned underflow
  because `||` short-circuits after the preceding
  `aligned_pos > reserved_size` clause. Reordering that chain silently
  reopens an OOB window. Worth a comment or restructuring so safety doesn't
  depend on clause order.
- ~`aether.h:2190` `str8_replace` — `count * (i64)(target.size - old.size)`
  subtracts two `u64`s and casts the possibly-wrapped result to `i64`.
  Correct today via the 2's-complement round trip, but reads like a bug and
  will break the moment someone "sanitizes" the intermediate value. Write it
  as `(i64)target.size - (i64)old.size`.~
- ~`aether.h:1255` `os_thread_create` — creator spins with no timeout waiting
  for the new thread's handshake. The same API exposes
  `ThreadPriority_TimeCritical`/`ProcessPriorityClass_Realtime`, which can
  starve that spin indefinitely with no diagnostic.~
- ~`aether.h:2664` `days_in_month_` — indexes `days[month-1]` with no bounds
  assert of its own; safe only because its one current caller pre-validates
  `month`.~
- ~`aether.h:508`/`1438` `arena_alloc_ex` — no overflow guard before
  `align_forward_u64(reserve_size, pagesize)`; a `reserve_size` near
  `U64_MAX` wraps silently to a tiny reservation instead of failing loudly.~
- ~`aether.h:416-422` ARM64 barrier — `atomic_load_acq_u64`/
  `atomic_store_rel_u64` emit a full `dmb` in both directions, stronger than
  the acquire/release the names promise. Safe, just worth a comment
  confirming it's deliberately conservative and not an oversight.~
- ~`iris.h:726-731` `socket_close` does a plain `s->handle = 0`. Checked
  against `docs/iris-networking-design.md` decision 11 directly: the
  documented usage pattern is actually safe — callers always
  `atomic_load_acq_u64` the shared handle into a fresh *local* `Socket`
  before calling `socket_close` on it, so the plain write never touches
  shared memory in the prescribed pattern. But nothing in the function or
  its signature stops a caller from passing a pointer straight into a shared
  `Socket` struct instead — worth a one-line doc-comment warning against
  that, since the failure mode if someone does it wrong is a silent data
  race.~

## C. Performance

- `str8`-by-value **parameters** (`str8_eq`, `str8_cmp`, `str8_trim*`,
  `str8_concat`, `str8_cut*`, `str8_split`, all `str8_to_*`, ~15 functions)
  force a stack copy on MSVC x64 specifically, since a 16-byte struct doesn't
  qualify for register passing under that ABI (System V on Linux/macOS
  passes the same struct in two registers for free — this is a Windows-only
  cost). Switching those parameters to `const str8*` would avoid the copy,
  but breaks passing a chained call's result directly as an argument (C
  can't take the address of a temporary, so `str8_eq(str8_trim(a), ...)`
  stops compiling) — for a handful of cycles per call, likely not worth
  losing that composability. Not recommended unless profiling shows a
  specific hot loop where it matters.
  (Return values were also considered and ruled out: a `str8`-returning
  function already goes through MSVC's hidden-pointer return convention,
  which is mechanically identical to an explicit out-param — there's no
  more-efficient alternative shape available. `ring_buffer_peek`/
  `ring_buffer_reserve` returning `view`/`bytes` by value are fine as-is.)
- ~~`iris.h` — every WinSock call (`send`/`recv`/`sendto`/`recvfrom`/`bind`/
  `listen`/`accept`/`connect`/`htons`/`ntohs`) re-resolves via
  `GetProcAddress` on **every call**, including inside the address-conversion
  helpers. This hits the hottest path in the library (every send/recv).
  Worth caching resolved pointers once at `net_init`.~~ (fixed — see
  CHANGELOG `[Unreleased]`)
- `aether.h` — `arena_push`, `arena_pop`/`arena_pop_to`/`arena_clear`, and the
  whole `ring_buffer_*` family are `AETHER_API` (out-of-line) despite being
  the hottest calls in the library. Atomics are correctly `static inline`;
  these aren't, which undercuts the cache-line padding already done on
  `RingBuffer`.
- No `AETHER_LIKELY`/`UNLIKELY` macro exists anywhere; none of the hot-path
  bounds/error checks hint the unlikely branch.
- `aether.h:1961` (author's own `todo`) `str8_find` is brute-force O(n·m);
  `str8_find_last` (1977) compounds it to worst-case O(n²·m) by repeatedly
  re-calling `str8_find` over shrinking suffixes instead of one reverse scan.

## D. API consistency & naming

- Return-value local naming: `ret` (`aether.h:902`) is the lone outlier
  among 13+ `result` locals; `ring_buffer_reserve` (`1656`) names its
  return-value local `out`, which everywhere else in the library means
  "out-parameter," not "value under construction." Separately, `iris.h`
  never uses `result`/`ret`/`res`/`rv` at all — it builds return structs as
  `Socket s = {0}; s.handle = ...; return s;` throughout, a different idiom
  from aether.h's `T result = {0}; ...; return result;` for structurally
  identical code.
- `str8_find`/`str8_find_last`/`str8_find_char` name their out-param `pos`,
  not `out`/`out_pos` — every other single-out-param function
  (`str8_to_u64`'s `out`, `os_file_size`'s `out_size`) uses `out`/`out_*`.
- Error-handling: four distinct shapes coexist — hard-abort-fatal (arena
  OOM), `b8`+out-param, struct-return-all-zero-is-failure, `NetResult`
  tri-state+count. Mostly explainable by failure category, but never stated
  as a rule — which is exactly the gap TODO.md's own "decide an
  error-handling convention" item names. Two outliers that look accidental
  rather than deliberate: `file_write` returns `u64` where `0` means *either*
  failure *or* a legitimate empty write (every sibling I/O function keeps
  those as separate channels); `net_addr_to_cstr` returns a bare
  `snprintf`-style length with silent truncation and no failure signal,
  unlike every other iris.h function.
- The "simple + full-options variant" pattern is spelled four different ways
  across the library: `_ex` suffix (`arena_alloc`/`_ex`, `str8_cut`/`_ex`), a
  bare required-flags param with no simple sibling (`str8_split`), a
  two-step `_alloc`+`_create` pair (`high_res_timer_*`), and an unsuffixed
  bounded wrapper over a general core (`str8_to_u8`.. over `str8_to_int`).
  Worth standardizing on one shape going forward.
- Type casing: `bytes`, `view`, `str8`, `datetime` are lowercase; every other
  struct (`Arena`, `RingBuffer`, `Str8List`, `NetAddr`, `Socket`) is
  PascalCase. Plausibly a deliberate "value/span types are lowercase" rule,
  but it's stated nowhere.
- Private-helper trailing-underscore convention (`arena_push_or_fatal_`,
  `str8_is_decimal_`, `is_leap_year_`) is broken by two neighbors doing the
  identical kind of work: `round_up_power_2` and `align_forward_u64`.
- `iris.h:253/706` `net_addr_to_cstr` declaration spells the param
  `char *buf` (space before star) — the only instance of that style in
  either file; everywhere else is `char* buf`.
- `aether.h:721` vs `2552` `file_unmap` — declaration names the param `map`,
  definition names it `v`. Harmless, but the only declaration/definition
  name mismatch in either file.
- `iris.h:502/524/591` vs `564` — `os_tcp_send`/`recv` and
  `os_udp_recv_from` clamp an oversized `u64 len` to `INT_MAX` and loop via
  the out-count; `os_udp_send_to` instead rejects outright above `INT_MAX`.
  Correct per-protocol (datagrams are whole-or-nothing), but nothing says so
  in a comment, so it reads as an inconsistency rather than a decision.

## E. Ergonomics / footguns

- `aether.h:581-582` `str8_from_view` has no doc comment and is referenced
  nowhere — not the header's own prose, README, tests, or examples. Looks
  like leftover debris from the v0.0.18 `str8`/`bytes`/`view` split rather
  than a deliberate addition; worth deciding whether to document it or drop
  it.
- `aether.h:1432` `arena_alloc_ex` with `ArenaFlags_CommitChunked` set and
  `granularity=0` silently substitutes 1-page chunking with no assert or
  documented default — an easy typo to make invisible.
- `aether.h:790-800` `console_signal_install` is a process-wide singleton
  with no query function; a second subsystem that tries to install gets a
  silent `false` with no way to check first.
- `aether.h:1486` `arena_push` has no `arena != NULL` assert, while its
  higher-level callers (`c_str`, `str8_push_copy`, `str8_concat`) all assert
  it at their own entry — inconsistent null-safety posture between the
  primitive and the layer built on top of it.
- `aether.h:674` `str8_to_int` (the general bounded-parse core) is declared
  *before* its typed convenience wrappers (`str8_to_u8`..`str8_to_i64`) — a
  first-time reader hits the harder, general form first, the opposite
  ordering from the arena API (`arena_push_t` before the general `_ex`).

## Open design decisions (not one-line fixes)

Two items above aren't mechanical — they're conventions to decide once and
apply everywhere:

- **Error-handling convention** (section D) — already an open TODO.md item;
  this review adds concrete evidence (the four-shape catalog) rather than
  resolving it.
- **`_ex`/simple-variant naming pattern** (section D) — four shapes currently
  in use for the same underlying "simple + full options" need.

(The `str8`-by-value ABI question originally listed here was reconsidered
during review — see section C. Return-by-value has no more-efficient
alternative on MSVC x64; by-value parameters have a narrow, Windows-only
cost that isn't worth trading away call-chaining for. No longer an open
question.)
