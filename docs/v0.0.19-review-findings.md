# v0.0.19 Pre-Release Review Findings — aether.h / iris.h / hermes.h

Date: 2026-10-15
Scope: `include/aether/aether.h` (3441 lines), `include/iris/iris.h` (863 lines),
`include/hermes/hermes.h` (518 lines, unreviewed until now), every file under
`tests/` and `examples/`, all of `docs/*.md`, `README.md`, `CHANGELOG.md`,
`TODO.md`, the root/`tests`/`examples` CMakeLists, and `scripts/release.ps1`.
Methodology: seven parallel review passes (two split `aether.h` correctness
front-to-back, one did a mechanical declaration-vs-implementation/banner-style
audit of `aether.h`, one covered `iris.h`+`hermes.h` together, one read every
test file's logic and cross-checked it against `tests/CMakeLists.txt`, one
cross-checked every doc file against current source, one built and ran
standalone C and C++ consumer programs against all three headers), followed by
direct source verification of the highest-stakes claims and a from-scratch
staleness audit of `docs/v0.1.0-review-findings.md`. Nothing in this file has
been acted on yet — it's a findings list, not a plan.

This review supersedes the open items in `docs/v0.1.0-review-findings.md`
(see section H) — most of that doc's "open" items turned out to already be
fixed with the doc never updated to say so. That doc is a working scratchpad,
not a maintained artifact; it should be refreshed or retired once the items
below are triaged.

## A. Must-fix correctness bugs

Confirmed by direct source reading and, where noted, reproduced two
independent ways: the project's own `ctest` suite, and a standalone
consumer program written for this review (`smoke_c.c`, `smoke_cpp.cpp`,
`smoke_bug_repro.c` — not checked in, available on request).

- **`aether.h:2713-2737` `args_parse`** — the keyword branch computes
  `has_inline`/`inline_val` unconditionally but only consults them when
  `spec->kind != ArgKind_Flag`. For a `Flag`-kind spec, `--verbose=false`,
  `--verbose=anything`, or `--verbose=` all hit `case ArgKind_Flag:
  *(b8*)spec->out = true;` — the attached value is silently discarded and
  the flag is always set `true`. Reproduced directly: `--verbose=false`
  parses successfully and leaves the flag `true`. Fix direction: when
  `kind == ArgKind_Flag && has_inline`, report a parse error instead of
  falling through.
- **`aether.h:2835` / `:2840` `args_parse`** — `ArgSpec::was_set` is written
  `true` at line 2835 but is **never reset to `false`** anywhere in the
  function; the required-field check at line 2840 (`if (specs[k].required &&
  !specs[k].was_set)`) trusts it directly. Any caller that reuses or copies a
  previously-parsed `ArgSpec` entry into a second `args_parse` call (a REPL,
  subcommand dispatch, anything building variants off a shared base table)
  inherits a stale `was_set == true` from the earlier call, and the required
  check silently passes even though the current `argv` never supplied that
  field. Reproduced directly: copying a spec that was satisfied in a first,
  successful parse into a second `argv` that omits it still returns success.
  Fix direction: loop over `specs[0..count)` and reset `was_set = false` at
  the top of `args_parse`, mirroring the reset `args_parse` already performs
  on `*out_err` for exactly this "no stale state across calls" reason.
- **`aether.h:2262` `str8_list_to_array`** — the loop asserts `node != NULL`
  *after* advancing past the final element: `result.items[i] = node->v; node
  = node->next; AETHER_ASSERT_(node);` on every iteration including the last,
  where `node` is correctly `NULL` (end of list) by construction. Crashes on
  **any** non-empty `Str8List` in a debug build. Present since the function's
  introduction (`3b832439`, v0.0.12) — every tagged release from v0.0.12
  onward ships this. Reproduced via `ctest`'s `str8_join` case (fails on both
  GCC and Clang builds) and independently via a from-scratch standalone
  program. Fix direction: assert before dereferencing on the *next*
  iteration instead of after advancing on the last one:
  ```c
  Str8Node* node = list->first;
  for (u64 i = 0; i < result.count; ++i) {
      AETHER_ASSERT_(node); /* catches a genuinely-too-short list */
      result.items[i] = node->v;
      node = node->next;
  }
  ```
- **`aether.h:3197` `high_res_timer_wait`** — `AETHER_ASSERT_(t &&
  t->armed);` fires immediately before `if (!t || !t->armed) return 0;`, the
  line that is supposed to make calling `wait()` on a never-armed timer a
  defined, safe no-op (CHANGELOG `[0.0.14]`: "is now a defined, safe no-op
  (returns 0)"). The assert directly contradicts the code one line below it.
  Introduced in the same commit (`7b7d249b`, v0.0.14) that added the
  safe-no-op behavior it undermines. Reproduced via `ctest`'s
  `timer_wait_without_arm_is_safe` and `timer_release_clears_state` cases
  (both fail, both compilers) and independently via a standalone program.
  Fix direction: delete the assert; the `if`-guard already implements the
  documented contract completely.
- **`aether.h:3058-3105` `file_stream_open` / `file_stream_ok` /
  `file_stream_flush`** — `file_stream_open` never sets `fs.err` when
  `os_file_open_for_write` fails, so `file_stream_ok()` (`return
  !fs->err;`) reports `true` for a stream that never opened. Once such a
  stream's buffer fills, `file_stream_flush`'s `if (!fs->handle || fs->len ==
  0) return true;` keeps reporting success while silently dropping every
  subsequent write — no crash, just data loss `ok()` never surfaces. This
  directly undercuts the feature's own documented purpose ("check once after
  a batch of writes... instead of threading a `b8` through every call").
  Fix direction: set `fs.err = true` in `file_stream_open` when the
  underlying open fails.
- **`hermes.h`, `os_serial_read`** — in the default `SerialTimeoutMode_Block`,
  `serial_read(p, buf, 0, &out)` maps `ReadFile`'s documented `read == 0` /
  `TRUE` (a legitimate zero-length no-op success) to `SerialResult_Timeout`
  instead of `SerialResult_OK`. Same bug class the project already fixed
  once for `ring_buffer_read` in `[0.0.13]` ("conflating 'asked for nothing'
  with 'not enough data'" — CHANGELOG's own words). `os_serial_write`'s
  zero-length case is unaffected, which sharpens the contrast.

## B. Why these went unnoticed (process gap, not just bugs)

- `scripts/release.ps1`'s only quality gate builds `-DCMAKE_BUILD_TYPE=Release`
  (`release.ps1:80-82`) and runs `ctest` against it. `AETHER_ASSERT_` compiles
  to `((void)0)` whenever `AETHER_BUILD_DEBUG` is off, which a Release
  configuration triggers by default — so this gate cannot see any of the
  three assert-based bugs in section A regardless of how long they've
  existed. It would pass vacuously today with all three still present.
- **28 real, compiling test cases across four files are never run by
  `ctest`** because each file's `tests/CMakeLists.txt` case list is a stale
  subset of that file's actual `g_cases[]` array — not an isolated slip, the
  same drift shape recurs in every affected file:
  - `test_strings.c`: 7 missing (`split_trim_foreach`, `cut_ex`,
    `parse_bases`, `parse_int_range`, `parse_int_wrappers`, `utf8_decode`,
    `utf8_width`)
  - `test_ring.c`: 7 missing, including `reserve_commit_roundtrip`,
    `reserve_seam`, `reserve_guards`, `reserve_cancel`,
    `reserve_partial_commit`, and **`write_zero_preserves_reservation`** —
    the named regression test for the zero-length-write bug CHANGELOG
    `[0.0.16]` calls out by name
  - `test_networking.c`: 5 missing, including **`socket_close_race`** — the
    dedicated regression test for this release's own `socket_close` TOCTOU
    fix
  - `test_timer.c`: 9 missing, including the entire `datetime`/`wall_clock_ns`
    suite (leap-year rule, epoch round-trip, out-of-range rejection) and
    `HighResTimer`'s spin-margin-clamping/`wake_time` tests (both
    CHANGELOG-documented fixes)

  Recommend syncing every `*_TEST_CASES` list in `tests/CMakeLists.txt` to
  its file's real `g_cases` before tagging — mechanical, no logic risk.
- `hermes.h` has essentially no automated coverage beyond a context-detection
  check. Its one functional case (`handshake`) is manual-only (needs a
  com0com-style pair) and exercises only `SerialTimeoutMode_Timeout` +
  default `SerialMode_RS232`. `SerialTimeoutMode_Block` (the default!),
  `SerialTimeoutMode_Poll`, `SerialMode_RS485`, and every parity/stop-bits
  variant have zero coverage of any kind — which is why the zero-length-read
  bug above went uncaught.
- `tests/CMakeLists.txt:11-14` has a dead, commented-out single-case
  `add_test(NAME arena COMMAND test_arena)` directly above the real per-case
  `foreach` loop that supersedes it. Harmless, but worth deleting while
  touching this file for the point above.

## C. Other correctness issues (lower severity / narrower reach)

- `aether.h:1377` (`os_thread_set_affinity`) — `(DWORD_PTR)1 << core_index`
  has no bound on `core_index`; `>= 64` is a shift-by-ue-width-of-type (UB in
  C, silently wraps mod 64 on real x86/x64 instead of failing).
- `aether.h:1560-1573` `arena_push` and siblings (`arena_pop`,
  `arena_pop_to`, `arena_clear`, `arena_begin_temp`, `arena_end_temp`) have
  no `arena != NULL` guard. The nearby `AETHER_ASSERT_(arena->pos <=
  arena->reserved_size)` doesn't substitute for one: when asserts are
  compiled out, the whole expression (including the `arena->` dereference)
  is never evaluated, so there is no NULL-safety net in either build
  configuration. Every other `*_t`/`*_array` layer built on top of
  `arena_push` does guard its own entry. Confirmed still open from the prior
  review.
- `iris.h:471` `os_tcp_listen` — the `SO_EXCLUSIVEADDRUSE` `setsockopt`
  return value is still explicitly discarded (`(void)os_ws2_.setsockopt(...)`).
  The one item from the prior review's section A with no corresponding fix
  anywhere in CHANGELOG.
- `iris.h:385-426` `os_net_init`'s failure path frees the WinSock DLL
  (`FreeLibrary(os_ws2_dll_); os_ws2_dll_ = NULL;`) but never `memset`s the
  cached `WS2API` table (unlike `os_net_shutdown`, which does). A caller
  that ignores `net_init`'s `false` return and calls e.g. `tcp_connect`
  anyway calls through dangling function pointers into unloaded module
  memory.
- `aether.h:3243-3249` `days_in_month_` — `AETHER_ASSERT_(month <= 12)` has
  no lower bound; `month == 0` underflows `days[month-1]`. Safe today only
  because its sole caller (`datetime_to_ns_since_epoch`, `aether.h:3306`)
  validates `dt.month` first — the same "safe by the one caller" fragility
  the prior review flagged, confirmed still true.
- `aether.h:3149-3173` `high_res_timer_alloc`/`_set_rate` assert `hz > 0` but
  have no upper bound. An `hz` large enough relative to `os_time_frequency()`
  rounds `period_ticks` to `0`; the next `wait()` divides by it
  unconditionally, crashing in both build configurations.
- `aether.h:2871-2879` `args_validate` + `:2696-2737` `args_parse` — a spec
  with `positional = true, kind = ArgKind_Flag` is accepted by both
  functions, but the parse switch's `case ArgKind_Flag` unconditionally sets
  the output `true` whenever that positional slot is reached, silently
  discarding the actual token. `args_validate` checks several other
  authoring mistakes but not this combination.
- `aether.h:2656-2682` vs `:2713-2718` — `args_has_option` and `args_parse`'s
  keyword branch duplicate the identical "split on first `=`; an empty
  inline value falls through to the next `argv` token" logic verbatim, down
  to the inline comment. The API-level split (quick raw check vs.
  table-driven parse) is justified; the mechanical split-and-fallthrough
  step itself is a clean candidate for one shared private helper.
- `hermes.h` `serial_close`'s doc comment claims the same cross-thread
  cancellation safety as `socket_close`, modeled on it — but
  `os_serial_port_open` opens with plain `CreateFileA` (no
  `FILE_FLAG_OVERLAPPED`), and Windows does not document `CloseHandle` from
  another thread as safely unblocking a pending *synchronous* `ReadFile`/
  `WriteFile` the way `closesocket` is documented to unblock a pending
  `recv`/`send`. Untested in either direction (the one `handshake` test is
  single-threaded).
- `hermes.h` `serial_write`'s shared doc comment ("Blocking, with a
  timeout") overstates what it does: only `os_serial_read` consults any
  `COMMTIMEOUTS` write field; `os_serial_write` never configures
  `WriteTotalTimeoutConstant`/`Multiplier`, so it blocks indefinitely
  regardless of `cfg.timeout_mode`. CHANGELOG confirms this is intentional —
  the code matches intent, but the header's own doc comment doesn't say so,
  which is hazardous specifically for RS485 (a stalled bus has no flow
  control to interrupt the block).
- `iris.h:742-748` `net_addr_to_cstr` returns a bare `snprintf`-style length
  with silent truncation and no failure signal, unlike every other `iris.h`
  function's explicit `b8`/`NetResult` channel. Confirmed still open.
- `iris.h:253` vs `:742` — declaration spells the parameter `char *buf`
  (space before star); the definition spells `char* buf`. The only instance
  of that style, and the two don't even match each other. Confirmed still
  open.

## D. Documentation vs. code

- **README's flagship HERMES example (`README.md:961,967`) uses a C99
  compound literal** — `serial_open(STR("COM10"), (SerialConfig){.baud=9600})`.
  This is not legal standard C++ (no cast-construct syntax exists there); it
  only "works" as a GCC/Clang vendor extension and fails under `-std=c++11
  -pedantic-errors` / MSVC `/permissive-`. `hermes.h` is explicitly dual
  C/C++, and the project has its own hard-won rule against exactly this
  pattern — compound literals were specifically removed from `aether.h` in
  `[0.0.9]` so the header passes `tests/verify_cxx11.cpp`'s pedantic probe.
  The flagship example for the newest module violates that guarantee.
- README:832 says TCP is implemented with "UDP to follow," while the same
  document shows a complete working UDP example at README:904-916 — UDP
  shipped in `[0.0.14]`. Self-contradictory within one file.
- README API-table / struct-sample gaps: `net_addr_parse_hostport`,
  `net_addr_to_cstr`, `net_addr_to_str8`, `socket_local_addr` (IRIS table);
  `thread_set_affinity` and the entire `ProcessPriorityClass`/
  `process_set_priority_class` API (Threads section); `arena_pop` (only
  `arena_pop_to` appears); `HighResTimer.wake_time` (struct sample shows
  `period_ticks, next_deadline, overrun, spin_margin, os_timer, armed` —
  missing both `wake_time` and `lateness`, which the prior review only
  caught one of).
- `docs/console-signal.md:3` ("designed, not yet implemented (2026-08-03)")
  and `docs/threads-design.md:1` ("implementation pending") are both false
  today — console-signal shipped in `[0.0.14]`, threads in `[0.0.13]`, both
  fully implemented with dedicated passing test files. These headers have
  been wrong for several releases.
- `docs/cereal-design.md` is not an orphaned future-module doc — side by
  side, its R1/R2/R3/R5/R6/R7 requirements map exactly onto `hermes.h`'s
  shipped shape; it's the pre-rename design doc for what became `hermes`,
  never updated to cross-link. One real gap worth a deliberate call: R4
  wanted three-way failure distinction ("no reply in time" / "device
  unplugged" / "other error"); shipped `SerialResult` only has
  `Timeout`/`Error` — "unplugged" and "other" both collapse into `Error`.
- `TODO.md:6,21` still describes the `str8_from_c_str` rename and the
  `str8`/`bytes`/`view` split as landing "in v0.1.0" — both actually shipped
  in `[0.0.18]`, two releases ago; `v0.1.0` doesn't exist (`VERSION` is
  `0.0.19-dev`). Confirmed still wrong, unchanged from the prior review.

## E. Code structure / aesthetics

- `aether.h`'s declaration region uses **three** banner styles, not two: a
  "heavy" style (`/*-------- W O R D S --------...*/`) for
  Context/Config/Types/Atomics/Arenas/Strings; a "light" style
  (`/* -------- W O R D S --- */`) for RingBuffer/CLI-Args/File-IO/Timers/
  Threads/Console-Signal; and RingBuffer's own banner, which is a one-off
  hybrid of both (shares the heavy style's dash count, the light style's
  padding). The switch happens exactly at the RING banner.
- Banner **text** drifts between a module's declaration and implementation
  banner, all three-line-sandwich style in the implementation region:
  `RingBuffer` → "RING / BUFFERS" (declared "RING/CIRCULAR-BUFFERS"),
  `Timers` → "TIMING" (declared "TIMERS"), `Console-Signal-Handling` →
  "CONSOLE-SIGNALS" (drops "-HANDLING"; also the only sandwich banner
  missing its trailing space before `*/`).
- Three confirmed declaration-vs-implementation ordering mismatches, all one
  root cause (implementation groups by internal callee-before-caller
  dependency even though forward declarations make that unnecessary;
  declaration groups for public reading order):
  - `str8_to_int`/`_u8`/`_u16`/`_u32`/`_u64`/`_i8`/`_i16`/`_i32`/`_i64`/`_f64`
    — declared general-core-first (`str8_to_int` then typed wrappers,
    matching the `arena_alloc`/`_ex` convention); implemented with
    `str8_to_u64`/`str8_to_i64` moved ahead of the general core.
  - `file_stream_ok`/`file_stream_valid` — declared in that order
    (`aether.h:780-781`), implemented swapped (`aether.h:3067-3072`).
  - `datetime_now` — declared 2nd of four in its family, implemented last
    (it's a one-line call into `datetime_from_ns_since_epoch`, which comes
    before it).
- Trailing-underscore convention for internal helpers: 11 compliant, **11
  non-compliant** (the prior review only knew of 2 —
  `round_up_power_2`/`align_forward_u64`, both still unprefixed). Sharpest
  example: `fmt_raw_` (correctly suffixed) is the helper extracted *for*
  `str8_fmtv`/`str8_push_fmtv`/`c_str_push_fmtv`/`str8_list_push_fmtv` —
  none of which carry the suffix themselves, despite the same privacy level
  and the same tightly-coupled family.
- `aether.h:829` and `:845` — identical `//todo(chris): should these be
  typedef u8 if we're not treating them like a bit feild?` sits directly
  above `typedef u8 ThreadPriority;` / `typedef u8 ProcessPriorityClass;`
  respectively — both already answered one line below, both still carry the
  "feild" typo. Trivial, high-confidence cleanup, confirmed unchanged from
  the prior review.
- `aether.h:767` vs `:3053` `file_unmap` — declaration names the parameter
  `map`; the definition names it `v`. The only declaration/definition name
  mismatch found in any of the three headers.
- `aether.h:588` `str8_from_view` — still referenced nowhere (not header
  prose, README, tests, or examples), still undocumented, confirmed
  unchanged since the prior review. Also has a cosmetic double-space typo in
  its own declaration (`static inline  str8`).
- `aether.h:719-720` bare `// --- paths ---` / `// todo(chris): do this`
  stub with nothing following it, confirmed still present.
- **Cross-file consistency check (good news):** `iris.h` and `hermes.h` both
  use the same "heavy declaration banner + three-line-sandwich
  implementation banner" pairing as `aether.h`'s unaffected sections, and
  both have declaration order matching implementation order **exactly**,
  verified exhaustively symbol-by-symbol in both files (not sampled). The
  banner-style drift in section E above is specific to `aether.h`, not a
  project-wide inconsistency.

## F. Orthogonality / redundancy

- **Confirmed non-redundant, no action needed:** `args_parse` (full
  `ArgSpec`-table-driven parsing/validation) vs. `args_has_flag`/
  `args_has_option` (raw presence/value checks, no table) — genuinely
  different use cases. `str8_fmt`/`str8_push_fmt`/`c_str_push_fmt` — three
  distinct output targets (caller buffer / arena `str8` / arena C-string),
  all funneling through one shared `fmt_raw_` core. `str8_to_u8`..`_i32`
  wrappers over `str8_to_int` over `str8_to_i64` — every bound constant
  checked correct for its width; `str8_to_u64`/`str8_to_i64` correctly stay
  standalone since `U64_MAX` doesn't fit `str8_to_int`'s `i64` domain.
- **One real implementation-level redundancy** (API-level split is fine,
  the mechanics underneath don't need to be re-derived twice): see section C,
  `args_has_option` vs. `args_parse`'s keyword branch.
- **`iris.h`/`hermes.h`: correctly not merged.** The two domains differ
  enough — Winsock needs runtime DLL loading plus ~15 cached function
  pointers because it isn't a Known DLL; serial needs none of that, since
  `kernel32`'s `CreateFile`/`ReadFile`/`WriteFile`/`SetCommState` are always
  linked. Forcing a shared "symbol resolution" abstraction onto `hermes.h`
  just to look parallel to `iris.h` would be over-engineering. Three smaller
  points have drifted between the otherwise-parallel designs, worth a
  one-line decision rather than a restructure: the `{0}`-is-invalid "+1
  handle bias" pattern (`os_socket_from_raw_`) has no counterpart in
  `os_serial_handle_from_raw_`, which stores the raw `HANDLE` directly;
  `serial_open` skips the `T x = {0}; x.field = ...;` zero-init idiom used
  everywhere else in both files; and `hermes.h`'s doc comments are less
  precise about per-operation semantics than `iris.h`'s (see section C).
- The "four different error-handling shapes" and "four different
  simple/full-variant naming spellings" noted by the prior review are both
  still accurate on a fresh recheck and still unresolved. Already an open
  `TODO.md` item ("Decide an error-handling convention"), not a new finding
  — but worth prioritizing now given this review's theme.

## G. Smoke-test methodology and results

Two standalone consumer programs (not part of the checked-in test suite)
exercised the public API the way a downstream application would: arena
(including nested and sibling-out-of-order temp scopes), strings (concat,
`str8_fmt` truncation, split, cut, numeric parsing), the full CLI-args
system (including the two bugs in section A, discovered this way before
being confirmed in source), file I/O and `FileStream`, the ring buffer both
single-threaded and across two real OS threads, `HighResTimer` and
`datetime`, console-signal install/uninstall, a real loopback TCP and UDP
round trip (including `socket_local_addr`), and — since this machine has a
com0com virtual null-modem pair configured (COM10/COM11) — a **real**
hardware-level hermes serial loopback, not just the error-path fallback.
A separate minimal program independently reproduced both section-A assert
bugs outside the project's own test harness.

Build matrix (`-Wall -Wextra -Wpedantic -Wsign-compare`, `-I include`):

| Build | Result |
|---|---|
| gcc `-std=c11` | clean (only `GetProcAddress`/`{0}`-init warnings, see below) |
| clang `-std=c11` | clean (1 warning, from the smoke-test harness's own `strncpy` use, not the library) |
| g++ `-std=c++11` | zero warnings |
| clang++ `-std=c++11` | 2 warnings, both from zero-initializing the Win32 `SYSTEM_INFO` struct's nested union via `{0}` — a third-party header shape, not an aether design issue |
| clang `-fsanitize=address,undefined` | built and ran clean, zero sanitizer reports across every section above |
| gcc sanitizers | failed to link (`cannot find -lasan`/`-lubsan`) — this MinGW distribution doesn't ship the sanitizer runtimes; an environment limitation, not a project issue |

The only two warning categories seen across the whole matrix, besides the
one `SYSTEM_INFO` case above, are expected and benign: `-Wcast-function-type`
from `GetProcAddress` results being cast to typed function pointers (an
essentially unavoidable pattern for runtime symbol loading on Windows,
appearing in both `aether.h`'s ring-buffer/`VirtualAlloc2` loading and
`iris.h`'s WinSock loading), and `-Wmissing-field-initializers` from the
`T x = {0};` idiom used throughout both headers (standard, well-defined C,
just a warning GCC/Clang's `-Wextra` is historically over-eager about).
